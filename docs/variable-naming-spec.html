Variable Naming Specification

Every variable in this file follows one grammar. Slots appear in a fixed order, each slot draws from a closed list of words, and unused slots are dropped — never reordered. Learn the grammar once and you can name any token without asking.

01

How to read a token name

Token names are paths. Figma turns each slash into a folder, so the name is both an address and a sentence. Position carries meaning — the third segment is always the same kind of word.

Component Variant / Intent Part Property State
Componentbutton / Variantprimary-brand / Particon / Propertyfg / Statehover

“The foreground colour of the icon inside a primary-brand button, while hovered.”

Read it left to right and it narrows: what thing → which version → which piece → which attribute → in what condition. Every token in the system answers those five questions in that order, even when it only needs two of them.

The one rule underneath all the others

Slots are positional, not labelled. Nothing in the name says “this part is the state” — you know it's the state because it's last. That is why order can never change and why words can't be borrowed between slots.

02

The four collections

Each collection answers a different question, and each may only reference the one above it. That chain is what makes light/dark and responsive modes work without touching a single component.

1 · Primitives1 mode: Value

What is it?

Raw values with no opinion about use. A blue is just a blue. Never bind these directly to a design — they exist to be referenced.

color/blue/500 spacing/16 font/size/24
2 · Semantic2 modes: Light · Dark

What does it do?

Meaning, decoupled from value. This is the layer components should reach for by default. Light and dark resolve here, so everything downstream themes for free.

bg/brand/hover fg/on-brand border/danger/subtle
3 · Component1 mode: Value

Where is it used?

Only created when a component needs to diverge from the semantic default, or has enough states to be worth naming. Built lazily, one component at a time.

button/secondary/bg/hover input/border/invalid
4 · Breakpoint3 modes: Desktop · Tablet · Mobile

How big, at this screen size?

Geometry and type scale only — never colour. Set the mode on a top-level frame and everything bound below it reflows.

grid/margin type/h1/size section/gap-y

Who may reference whom

FromMay alias toMust never alias to
PrimitivesNothing — raw values onlyAny other collection
SemanticPrimitivesComponent, Breakpoint, another Semantic token
ComponentSemanticPrimitives directly (colour only — see note)
BreakpointPrimitivesSemantic, Component
The one sanctioned exception

There is no semantic layer for spacing, radius, or border-width — only colour has one. So components bind those straight to Primitives: spacing/16 for padding, radius/8 for corners. This is intentional, not drift. Colour is the only thing that changes between light and dark, so colour is the only thing that needs a meaning layer.

03

The grammar

Each tier has its own slot sequence. Within a tier the order never varies. A slot is dropped when the token has only one possible value for it — the remaining slots keep their positions.

TierSlot sequence
Primitiveproperty / family / step
Semanticproperty / intent / role
Componentcomponent / variant / part / property / state
Breakpointgroup / role / property

Omission in practice

The component tier has five slots but most tokens use three. Watch what drops and what stays put:

Componentcheckbox / Partindicator / Propertybg / Statechecked

No variant slot — a checkbox has only one visual variant. The part slot still sits second, exactly where it would if a variant existed.

✓ Correct
card/bg card/header/border

Two slots or three — the property is always the last non-state slot.

✕ Wrong
card/bg/header

Part after property. Now segment 2 means “property” in one token and “part” in another — position no longer tells you anything.

04

Slot reference

What belongs in each slot, and the edge cases that come up most.

Component

The thing a designer would name in a spec. Singular, always. If the name is two words, hyphenate — never split across slashes.

buttoninputcheckboxradioswitchselecttextareacardmodaltooltiptoastbadgeavatartabstablemenusliderprogressbreadcrumbpagination

Open list. New components are added freely — this is the only slot that grows without an amendment.

Variant

Which version of the component. Present only when the component has more than one and they need different tokens.

primary-brandprimary-neutralsecondarytertiarydestructiveghostoutlinepillunderline

pill and underline are navigation shape variants — they describe how a nav item renders its selection affordance, not its intent. Currently used by tabs/*.

Sizes are not variants. Small/medium/large change spacing and type size, which come from Primitives directly. They never produce their own colour tokens.

Part

A named piece inside the component. Only create one when the piece needs a token the root doesn't.

iconlabelindicatortrackthumbheaderbodyfooterdividerplaceholdercaretmenu-itemrowcell

Property

The attribute being set. Closed list — never invent a synonym. This is the slot where systems rot fastest: bg, background, surface, and fill all meaning the same thing is how a 200-token system becomes unusable.

bgfgborderringshadowradiusgappadding-xpadding-ysizeborder-widthline-heightletter-spacing
UseNotCovers
bgbackground, surface, fillAny frame or shape fill
fgtext, color, content, inkText and icon colour — one token serves both
borderstroke, outline, lineStroke colour
ringfocus, halo, glowFocus indicator drawn outside the border
sizewidth, height, dimensionSquare dimensions (icons, avatars, controls)

State

The interaction or condition. Always last. Closed list. default is implicit and is never written.

hoverpressedfocusselectedcheckedindeterminateexpandedinvalidloadingread-onlydisabled

States may compose. Two states join as <state>-<state> when both are in the list above, written in the order they appear in that list — so hover-selected, never selected-hover. Compose only when the combination carries a value neither state carries alone; a selected table row that darkens further on hover is the case this exists for. Fixing the order by the vocabulary means there is exactly one legal spelling per combination.

Intent — semantic tier only

What the colour means. Maps one-to-one onto a primitive hue; that mapping is fixed system-wide.

IntentHueUsed for
neutralgraySurfaces, text, borders — the default
brandbluePrimary actions, focus
linkblueHyperlinks. Shares brand's hue today but holds its own token, so re-branding does not silently restyle every link.
successgreenConfirmation, positive status
warningyellowCaution, needs attention
dangerredDestructive actions, errors
infopurpleNeutral information, AI features
scrimalpha black / whiteTranslucent layers — modal overlays, hover washes. The one intent whose value is an alpha, not a hue.
on-<intent>—Foreground sitting on that intent's fill

Orange and pink are unassigned. They are available for data visualisation or a future intent — but the moment one is used for meaning, it gets an intent name here and stops being free.

Role — semantic tier only

How prominent, within an intent. An ordered scale, so new steps insert cleanly:

RoleWeightTypical use
mutedFaintestBarely-there dividers, de-emphasised text
subtleLightTinted backgrounds, status banners
tintLight, one step upThe second faint step, where an intent has two
secondaryBelow baseSupporting copy, form labels
bodyJust below baseLong-form reading. Deliberately a step lighter than default so body copy sits below headings in the hierarchy rather than competing with them.
defaultBaseThe normal case — written out at this tier
emphasizedAbove baseFirst step past the resting border weight
strongHeavierEmphasised borders, hover surfaces
boldHeaviest before solidThe strongest non-solid border
emphasisSolid, high contrastFilled badges, solid buttons
inverseFlippedContent on an opposite-mode surface
disabledoff-scaleThe unavailable case. Deliberately not a point on the ordering — it is a condition, and it is the one role that never composes with a state.

Not every intent uses every step. The scale is an ordering, not a checklist — bg uses the faint end, border uses the middle. What the ordering guarantees is that a new value always has an obvious place to slot into, and that two people never invent two words for one step.

Three steps, three words — earn them

emphasized, strong and bold are adjacent steps on the border ramp and read as synonyms in isolation. They are in the list because the file genuinely holds three distinct border weights above default. If a ramp ever drops to two steps, drop the middle word with it — three names for two values is exactly the rot §5 exists to prevent.

One inconsistency to know about

At the semantic tier default is written (bg/neutral/default) because the role slot must always be filled. At the component tier the default state is omitted (button/secondary/bg). Different slots, different rules — role is required, state is optional.

Numbers or words?

Use numbers when the scale might gain steps between existing ones — colour ramps, spacing, font sizes. A 350 can always be inserted. Use words when the set is small and complete — thin/default/thick, regular/medium/semibold/bold. Never use light / dark as step names; they break the instant a step is added on either end.

06

The twelve rules

Everything above is descriptive. These are prescriptive — they settle the hard cases.

01One state per token

Compound states hyphenate inside the state slot, base condition first. Never split across slashes.

✓ Do
menu/item/bg/selected-hover
✕ Don't
menu/item/bg/selected/hover

Keeps the slot count fixed at five. Splitting states makes depth unbounded.

02Disabled always wins and never combines

There is no hover-disabled. Disabled is terminal — nothing can be hovered, focused, or pressed while disabled.

Prevents a combinatorial explosion of impossible states.

03One segment per slot

Compound names hyphenate: menu-item, padding-x, primary-brand. Never menu/item.

Nesting parts inside parts makes depth unbounded and breaks positional reading.

04Never encode the value

Outside Primitives, a name describes meaning, not appearance.

✓ Do
bg/brand/default
✕ Don't
bg/blue-500button/bg/dark-navy

The entire point of the tier. A value-named token can't be rebranded or themed.

05Depth budget: five segments

Hitting six means the “part” is really its own component. Decompose instead of nesting.

✕ Six segments
table/row/cell/icon/fg/hover
✓ Decomposed
table-cell/icon/fg/hover

This is the rule that keeps the system honest as it grows. Depth pressure is a signal to split a component, not to add a level.

06Shared value → move it up a tier

If two components would define the same value, it belongs in Semantic. Component tokens exist for divergence, not repetition.

Disabled styling is the clearest case: every component's disabled state is identical, so it lives at bg/neutral/muted, not as fifteen separate component tokens.

One rule, one place to change it, and disabled looks the same everywhere — which is what users expect.

07Don't create a token you use once

If a component binds a semantic token directly and never diverges, no component token is needed. Add one only when the value must differ from the semantic default, or when a state ramp makes the intent unclear at the call site.

Pre-building the component tier is the single biggest cause of token bloat.

08Singular, always

button not buttons, icon not icons. A token names one thing.

Mixed plurality means guessing, and guessing means duplicate tokens.

09Foreground covers text and icons

One fg token serves both. Only split when they genuinely differ — a muted icon beside full-contrast text — and then use the part slot: button/icon/fg.

Splitting by default doubles the colour surface for no benefit.

10Sizes never get colour tokens

Small, medium, and large change spacing, radius, and type size — all bound straight to Primitives. A size never produces its own colour token.

Otherwise every colour token triples for no reason.

11Effects are styles, not variables

Figma variables cannot hold shadows or gradients. Elevation goes in effect styles named Category/Name in Title Case — Button/Raised, Shadow/md, Focus/Ring. Bind their colours to variables where possible.

Different Figma primitive, so different naming convention — Title Case signals “this is a style, not a variable.”

12If you have to ask, it goes in Semantic

When it's unclear whether something is a semantic or component token, put it in Semantic. Promoting later is a rename; demoting later means updating every binding.

Asymmetric cost. Guess in the direction that's cheap to undo.

Sorting behaviour

Figma sorts alphabetically within each folder, which has two consequences worth designing around:

  • Numeric ramps sort wrong — 100 lands before 50. Accepted; the ramp is short enough to scan. Do not zero-pad.
  • States cluster under their property because they're a suffix on the same folder. This is exactly why states are the last slot rather than a top-level folder.
08

Where does my token go?

Work down. The first “yes” is your answer.

Q1

Is it a raw value with no meaning attached?

Yes → Primitives. property / family / step

No → continue

Q2

Does it change between Desktop, Tablet, and Mobile?

Yes → Breakpoint. Geometry and type only — if it's a colour, the answer is no.

No → continue

Q3

Would more than one component use this exact value?

Yes → Semantic. property / intent / role

No → continue

Q4

Does this component actually need to differ from the semantic default?

No → Bind the semantic token directly. Create nothing. (Rule 07)

Yes → Component. component / variant / part / property / state

Q5

Is your name six segments long?

Yes → Stop. Split the inner part into its own component. (Rule 05)

No → Ship it.

The most expensive mistake

Creating component tokens for a component you haven't built yet. You will guess the states wrong, and the wrong names will be bound into files before anyone notices. Build the component first, add tokens when a real need appears.

12

Scopes and code syntax

Two settings that make a token usable. Both are mechanical — derive them, don't decide them.

Scopes

Scopes control which Figma pickers a variable appears in. Tight scopes are what stop a designer accidentally binding a spacing token to a corner radius.

PropertyScopes
bgFRAME_FILL, SHAPE_FILL
fgTEXT_FILL, SHAPE_FILL (shape covers icons)
border, ringSTROKE_COLOR
gap, padding-*GAP, WIDTH_HEIGHT
radiusCORNER_RADIUS
border-widthSTROKE_FLOAT
Font size / weight / familyFONT_SIZE / FONT_STYLE / FONT_FAMILY
Line heightLINE_HEIGHT
Optional hardening

Once the semantic layer is complete, primitives can be scoped to [] — they vanish from every picker, making semantic tokens the only bindable option. Strongly recommended, because a designer binding a fill straight to color/blue/500 is exactly the drift that breaks dark mode later.

Code syntax

Every variable carries a WEB code syntax value. Derive it mechanically: replace slashes with hyphens, prefix with --, wrap in var().

VariableCode syntax
color/blue/500var(--color-blue-500)
bg/brand/hovervar(--bg-brand-hover)
button/secondary/bg/hovervar(--button-secondary-bg-hover)

No exceptions, no hand-tuning. The moment one token's code syntax stops matching its path, nobody can trust any of them.

13

Modes

Modes are how one token holds several values. Which collection gets modes is a structural decision, not a preference.

CollectionModesWhy
PrimitivesValueRaw values don't theme. One mode, named neutrally.
SemanticLight · DarkThe only place theming happens.
ComponentValueInherits theming through its aliases. Adding modes here duplicates work.
BreakpointDesktop · Tablet · MobileGeometry varies by screen, independently of theme.

Rules

  • Never add modes to Component. If a component needs different values in dark mode, the semantic token it points at should change — not the component token.
  • Modes multiply, they don't add. Theme × breakpoint in one collection means six columns to maintain. Keep them in separate collections and Figma resolves the combination for you.
  • Mode limits are plan-dependent. Professional caps at four modes per collection. Two and three both fit; a brand-theming tier with many brands would need Organization.
  • Effect styles have no modes. A shadow tuned for light surfaces reads weakly on dark. Either accept it or maintain a parallel Dark style set applied by hand.
14

Lifecycle

Adding, changing, and retiring tokens — plus how to amend a closed vocabulary.

Adding a token

  1. Run §8. Confirm the tier.
  2. Check the closed vocabularies. If your word isn't there, either use the existing word or start an amendment — do not invent one quietly.
  3. Search existing tokens for the concept before creating. Most “new” tokens already exist under a name you didn't guess.
  4. Set scopes (§12) and code syntax (§12) at creation, not later.
  5. Alias to the tier directly above (§2). Never skip a tier for colour.

Renaming

Figma preserves all bindings through a rename — it is non-destructive. The real cost is muscle memory and any code that has already shipped against the old name. Rename freely while the system is young; batch renames once components are in production.

Deprecating

Never delete a token that is still bound anywhere. Instead:

  1. Create the replacement.
  2. Repoint the old token's value to alias the new one — every existing binding keeps working.
  3. Prefix the old name with _deprecated/ so it sinks to the bottom of the picker.
  4. Delete only once nothing references it.

Amending a closed vocabulary

Adding a word to Property, State, Intent, or Role is a system-level change. Before adding, answer all three:

  1. Is it genuinely absent? Most proposed words are synonyms of an existing one. surface is bg. active is pressed or selected — decide which and use that.
  2. Will it be used more than twice? A word for one token is an override, not a vocabulary entry.
  3. Where does it sit in the order? Role words must slot into the muted → inverse scale. If it doesn't fit the scale, it isn't a role.

If all three pass, add the word here and in the file, in the same change. A vocabulary that lives only in someone's head is not closed.

The largest divergence, and it is systemic rather than a handful of typos: no variable in the file uses a neutral intent segment. The spec requires the intent slot to be filled; the file treats neutral as implicit throughout.

17

Cheat sheet

Print this. Everything else is elaboration.

Name a variable in four steps

  1. Pick the tier — raw value → Primitives · shared meaning → Semantic · one component only → Component · varies by screen → Breakpoint
  2. Fill the slots in order — component / variant / part / property / state
  3. Drop what you don't need — never reorder what's left
  4. Check it's ≤ 5 segments — if it's 6, split the component

Property — closed

  • bg · fg · border · ring · shadow
  • radius · gap · padding-x · padding-y
  • size · border-width
  • line-height · letter-spacing

Intent — closed

  • neutral · brand · success
  • warning · danger · info
  • on-<intent>

State — closed, always last

  • hover · pressed · focus
  • selected · checked · indeterminate
  • expanded · invalid · loading
  • read-only · disabled
  • (default is never written)

Role — ordered scale

  • muted → subtle → default
  • → strong → emphasis → inverse

Never

  • Put a value in a name — bg/blue-500
  • Put state anywhere but last — button/hover/bg
  • Invent a property synonym — surface, fill, text
  • Combine anything with disabled
  • Give a size its own colour token
  • Create a component token that just repeats a semantic one

Glossary

For anyone new to token systems.

TermMeans
TokenA named design decision. In Figma, a variable.
PrimitiveA raw value with no meaning attached — a specific blue, a specific 16px.
Semantic tokenA token named for what it means, pointing at a primitive. Where theming happens.
AliasA token whose value is another token rather than a literal. The chain that makes theming work.
SlotOne position in a token name, between slashes. Meaning comes from position.
Closed vocabularyA fixed list of allowed words for a slot. Changing it requires an amendment.
ModeA column of values inside a collection — Light and Dark, or Desktop/Tablet/Mobile.
CollectionA group of variables sharing a set of modes. This system has four.
ScopeWhich Figma pickers a variable shows up in. Tight scopes prevent mis-binding.
Code syntaxThe name a developer sees in Dev Mode. Derived mechanically from the path.
IntentWhat a colour means — brand, success, danger. Fixed to one hue each.
RoleHow prominent, within an intent. An ordered scale from muted to inverse.
PartA named piece inside a component that needs its own tokens.
Synonym driftThe same concept named several ways. The main cause of design-system decay.
